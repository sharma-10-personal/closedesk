The goal

Start the day with a short list of real exceptions — each with a cause, ₹ at risk and a proposed fix

  • Most rows match automatically, inside the database, in seconds.
  • Leftovers are classified into named break types, not "unmatched".
  • Breaks are grouped by root cause, so one fix can clear thousands of rows.
  • The queue is ranked by rupees at risk and deadline, not by row order.
  • An agent proposes the fix. A human approves or rejects. Everything is audited.

Effective use of Exasol Personal

“The sovereign analytics database, built for the agentic era.” CloseDesk uses all three parts.

Sovereign by default

NPCI, ledger and merchant files, matches, proposals, decisions and the audit log all live in one local CLOSEDESK schema. No cloud account, no API key, nothing sent out.

In-memory SQL

Nine plain SQL stages do the whole match, classification, grouping and ranking. No Python loop over transactions. 6.65s for ~3M rows across three sources on a 2-vCPU local VM.

Agents on your own data

The agent reads breaks from Exasol and writes proposals back. The gate decision, the human approval and audit_log are Exasol rows too.

  • Python only validates files, bulk-loads them with pyexasol, and serves the UI. Every screen queries live Exasol state.
  • Not used yet: UDFs and S3/Iceberg connectors. Next: run the same SQL on a multi-node BYOC cluster at 10M+ rows.

Governed agent

The agent proposes. A human decides. Exasol remembers.

Allow · ≤ ₹50,000

Offered for one-click approval by the analyst.

Escalate · up to ₹5,00,000

Flagged for a supervisor before anyone acts.

Block · above that

Approve is disabled in the UI and refused in code. Manual process only.

  • The agent can only choose from an allow-list of five actions in config/policy.yaml.
  • Every proposal, approval and rejection is written to audit_log with before and after state.
  • Explanations come from templates and SQL labels, so it runs with no LLM and no API key.
